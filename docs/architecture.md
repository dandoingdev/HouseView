# Architecture

A contributor's map of HouseView. For the user-facing behaviour read the [configuration](configuration.md) and
[overviews and screensavers](screensavers.md) pages; for adding code read the [widget API](widget-api.md), the
[overview API](overview-api.md) and [CONTRIBUTING](../CONTRIBUTING.md).

## Goals

* **One file to install.** `npm run build` bundles everything (JavaScript, one stylesheet, the three wallpapers as
  `data:` URIs) into `dist/houseview.js`. No server component, no external fonts, images or scripts.
* **A widget is a folder.** Each widget and overview owns its markup, actions, strings, CSS, fixtures, tests and
  documentation. The controller and `core/` know no widget names; adding a folder adds the widget everywhere.
* **Bounded pages.** The carousel packs widgets into screen-sized pages and renders one page at a time.
* **Cheap on weak tablets.** Change detection compares only what the card shows, patching keeps DOM and images alive, a
  single one-second ticker serves every card, and a covering overview stops all other work.
* **Home Assistant conventions.** Native card picker and editor, `tap_action` family, translations, theme-aware.

## Repository layout

```
src/
  index.js            bundle entry: registers widgets, overviews and editors, defines the elements, prints the banner
  define.js           defineOnce() and registerCustomCard(): safe when the resource is loaded twice
  version.js          VERSION, injected from package.json by the build
  config/             validate.js (the setConfig pipeline), convert.js (cards <-> widgets)
  controller/         <houseview-card>: one class made of mixins, one file per concern
  core/               the engine: registry, context, dispatch, i18n, hass signature, ticker, idle manager,
                      overview registry, subscriptions, action config, gestures, performance
  elements/           <houseview-widget-card> (the generic card) and the per-widget card tags
  editor/             <houseview-editor> and <houseview-widget-editor>, the forms
  layout/             pack.js (balanced rows, first-fit packing) and index.js (pages, columns)
  widgets/<type>/     one folder per widget (+ _shared/)
  overviews/<type>/   one folder per overview (+ _shared/)
  i18n/en.js          core English strings
  styles/             core/, layouts/, surfaces/, control-family.css, phases.json
  assets/             the three wallpapers (inlined into the CSS at build time)
tools/                build, generators, linters, test runner, benchmark (see tools/README.md)
tests/                unit, contract, overview and browser suites (see tests/README.md)
docs/                 these pages; docs/widgets and docs/overviews are generated
examples/             dashboards that load
themes/houseview.yaml an optional Home Assistant theme
```

`src/widgets/index.js`, `src/overviews/index.js` and the two test manifests are generated by `npm run gen`.
`docs/widgets/*` and `docs/overviews/*` are generated by `npm run gen-docs` from the READMEs next to the code.

## Layers and who may import whom

```
widgets/, overviews/  ->  core/ and their _shared/ only
core/                 ->  never controller/, editor/, elements/
controller/, elements/, editor/  ->  core/, config/, layout/
```

ESLint (`no-restricted-imports`) and the contract linters enforce this. Service calls reach Home Assistant only through
`ctx.call` in `src/core/context.js`; confirmations only through `src/core/confirm.js`.

## Data flow

### Configuration

```
Home Assistant calls setConfig(raw)
  -> config/validate.js   cards -> widgets (convert.js), extension checks, card options, pages,
                          per widget: type known, option enums, def.validate, entity rule, size, tap/hold/double-tap,
                          alias folding and def.normalize; then validateScreensaver (the screensaver block and the
                          timer_display / music_screensaver options)
  -> card._config         the validated config (or the old one is kept and an Error message shows in a red card)
  -> resolvePerformance   'lite' or 'full' for the life of this config
  -> screensaver setup    normalizeScreensaver(): explicit entries, then implicit ones for timer and music widgets
  -> _render()
```

`cards` is the shape users write; internally the controller works with a `widgets` list in which every HouseView card is
a widget (`{type, entity, page, ...}`) and every other Home Assistant card is a `native_card` that keeps the original
under `_card`.

### hass to DOM

```
set hass(hass)
  -> _applyHass: remember hass; forward hass to native cards (unless an overview covers the card)
  -> widget onHass hooks (for every configured widget, also on other pages: the timer must notice a finish)
  -> hassChanged(): compare only the watched entity states plus language, units, dark mode and time zone
       'reference' (identity; Home Assistant replaces a state object on every change) or 'deep' (JSON; mock hass);
       state_compare picks the mode, auto = reference when hass.connection exists
  -> unchanged: stop. Changed: _updateWidgets() (patch in place) or _render() (rebuild structure)
  -> _screensaverHass(): sync overview data leases, auto wake, event predicates
```

`_render` builds the shell, the page face and the page navigation for the current page from the screen model
(`controller/screen-model.js` calls `layout/buildScreens`). For each placement a `houseview-widget-card` element is
created and **bound** to the controller; its `update()` calls the widget's `render(ctx)`, and the result is compared with the
previous markup and **patched** into the existing DOM (`controller/patch.js`) so focus, loaded images and animations
survive. A widget may take over with its own `patch` hook (the camera). After the DOM is in place the `afterRender` hooks
run, then a layout pass sizes the clock dials and the grid.

A standalone widget card (`custom:houseview-light-card`) hosts a nested `houseview-card` in single-widget mode, so one
code path serves both.

### Click to service

```
click on button[data-action]   (one delegated listener on the shadow root, controller/events.js)
  -> a click right after a swipe, gesture or overview dismissal is swallowed
  -> tap_action configured on that widget's primary button?  -> core/action-config.js (more-info, toggle,
       perform-action, navigate, url, none; hold and double tap through core/gesture.js)
  -> otherwise card._act(action, entity) -> core/dispatch.js:
       resolve the owner in the registry -> immediate? -> pending/availability -> guard -> confirm
       -> mark pending -> run (ctx.call -> hass.callService) -> "Could not complete action: ..." on error
       -> clear pending -> refresh
```

### Time

`core/ticker.js` is the one shared one-second ticker. Every card subscribes instead of owning an interval; it runs only
while something is subscribed and the document is visible, and a hidden page gets one immediate tick when it returns. Widget
`tick` hooks are throttled to their `every` and skipped while an overview covers the card. The idle manager, the event
predicates and the overview ticks ride the same tick.

### Overviews

`controller/screensaver.js` hosts overviews: the idle manager (`core/idle.js`), the layer, event predicates, the
one-off manual layers and the per-instance data leases (`core/overview-session.js`, `core/subscriptions.js`). The
controller makes exactly five calls into it (set config, connect, disconnect, hass, end of render). With no `screensaver`
block and no timer or music widget it allocates nothing. See the [overview API](overview-api.md).

An `interactive` overview (the home overview) is the one kind that has buttons in card mode. They go through the normal click
path: `goto-widget` (a core feature action that looks the widget up in the controller's `_screens` and calls `_setPage`),
`camera-grid` and `run-action` run through `core/dispatch.js` with their usual guards. Its `watch(options, config)` receives the
card config, so the change detection in `core/hass-signature.js` watches the entities of every widget it is built from.

## CSS phases

All CSS is assembled into one stylesheet with a fixed cascade order. `src/styles/phases.json` lists the phases in order
(`base`, `adaptive`, `carousel`, `surface-teal`, `carousel-widgets`, `canvas`, `layout-page`, `night`, `tablet`,
`widgets-late`, `gallery`, `lifted`, `reuse`, `nav-compact`, `overviews`). Each CSS file is a sequence of sections that
start with `/* @phase <name> */`. `tools/assemble-css.mjs` concatenates, phase by phase, the sections sorted by group
(core, layouts, surfaces, control family, widgets, overviews), then file path. `@family(icon-tile)` expands to the list of
widgets that declare that family. `@import`, `@layer` and `url()` outside `src/styles/surfaces` are hard errors.
A file without a marker lands in `carousel-widgets`; an overview file must carry `@phase overviews`.

The result is delivered to each card as a `<link>` to one shared Blob URL (so the browser parses it once), with an inline
`<style>` fallback when blobs are blocked. The stylesheet is built for Chrome 105 and whitespace-minified only, because
syntax minification rewrites colours.

Order is behaviour: a later phase wins at equal specificity, which is why widgets must stay at specificity `(0,3,0)` or
below, without `!important`; `npm run check:widgets` and `npm run check:overviews` check this.

## Build, packaging, release

| Command | Result |
| --- | --- |
| `npm run build` | Production bundle `dist/houseview.js`, fully minified (local names too), plus `houseview.js.map` and `houseview.js.sha256` |
| `npm run build:dev` | Unminified bundle with an inline source map; what the browser tests run against |
| `npm run build:min` | The production build into `dist-min/`, so the tests can run against the shipped bytes |
| `npm run dev` | Watch build plus a local static server on 127.0.0.1:8765; regenerates the index files when folders change |

The version comes from `package.json` (esbuild define `__HV_VERSION__`) and is printed once in the browser console as a
banner. `npm run size` warns when the bundle outgrows its budget. `tools/release.mjs` checks that the tag equals the
package version, that `CHANGELOG.md` has a section for it and that `dist/` is a production build; the release workflow
(`.github/workflows/release.yml`) runs the whole test suite, builds and attaches the allow-listed files. HACS installs
`houseview.js` from the release (`hacs.json`).

## Where Home Assistant's internals are touched

Everything else uses public APIs (the card element contract, `hass`, `hass.callService`, `hass.callWS`, subscriptions
through `hass.connection`). These places reach into frontend internals, are feature-detected, never throw and are
the first suspects after a Home Assistant frontend update:

* `controller/tablet-chrome.js`: hides the sidebar and header by reaching into the shadow roots of
  `home-assistant`, `home-assistant-main`, `ha-drawer` and `hui-root` (`?tablet=1`, `tablet_mode`).
* `controller/screensaver.js` `isEditMode()`: recognises the edit-mode wrappers (`hui-card-options`, `hui-card-preview`,
  `hui-card-edit-mode`) so a screensaver does not start while you edit.
* `controller/native-card.js`: `window.loadCardHelpers()` to create native cards.
* `editor/native-stack.js`: loads Home Assistant's own stack-card editor (`hui-stack-card-editor`) for the page editors.
